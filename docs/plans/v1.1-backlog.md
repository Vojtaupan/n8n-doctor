## 1. `sheets-user-entered-for-data`: detect the platform default

**Deferred from the zero-firing audit, 2026-08-27. This is the largest known gap
in the tool's coverage.**

The rule fires on a Google Sheets write that *sets* the cell-format option to
`USER_ENTERED`. It does not fire on a write that sets nothing - but from node
`typeVersion 4.1` onward, **`USER_ENTERED` is the platform default**
(`cellFormatDefault` returns `RAW` below 4.1, `USER_ENTERED` at and above it), so
those writes are `USER_ENTERED` writes too. That boundary is read from n8n's
source rather than executed against a running instance, so it is inferred, not
measured - two independent readings agreed and 16 corpus nodes are consistent
with it, and confirming it on a live instance is step one of this item.

Measured on the validation corpus: of **172** Sheets write operations, **149 set
no cell-format option and all 149 are at typeVersion >= 4.1** (61 at 4.5, 88 at
4.7). True incidence is therefore about **280 nodes, 6.346%**, against the 131
(2.969%) the rule reports today.

**Why it was not done in v1.** At 6.346% the rule breaches its own `warning`
bound of 5%. Shipping the extension would force one of two things, and neither
belongs in a calibration pass:

- **Move the bound to fit the rule.** This is precisely the anti-pattern the gate
  exists to prevent, and the gate's own proof-of-work section is the argument
  against it.
- **Re-decide the rule's severity.** Defensible - `info` would clear the bound
  comfortably - but that is a product judgement about how loud this finding
  should be, not a measurement.

**What to decide first, before writing any code:** is a Sheets write that relies
on the version default the same defect as one that asks for `USER_ENTERED`
explicitly? The data corruption is identical. The author's intent is not: one
chose it, the other inherited it from a default that changed under them at 4.1.
That question decides the severity, and the severity decides whether the
extension fits the bound.

Two smaller misses in the same rule, worth folding into the same change:

- One corpus node configures the option through n8n's structured
  query-parameter form (`queryParameters.parameters[]`), where the option name is
  a `name` field rather than a parameter key or a string assignment.
- A v2 Sheets node setting the inert `valueInputMode` to `RAW` while relying on
  the default is a `USER_ENTERED` write that stays silent. No corpus node does
  this today, but the shape is reachable.

Full disclosure of the gap is in the limits section of `docs/calibration.md`.

## 2. `if-v2-missing-left-value`: decide whether the Switch node is in scope

**Raised by the zero-firing audit, 2026-08-27. Open question about the rule's
premise, not a known defect.**

The Switch node carries the same condition component as the IF node, and **23 of
90** `rules.values[].conditions.options` objects in the corpus lack `leftValue` -
the exact shape this rule treats as an `error` on IF nodes.

The rule was deliberately not extended, for two reasons. Those 23 nodes exist in
exports of working workflows, which contradicts the premise that n8n's creation
API rejects the shape - so either the requirement is IF-specific, or the field
note behind the rule has a narrower scope than the shared component. And 23 new
error findings would take the error count from 22 to 45, breaching the gate's
absolute cap of 25.

Resolve the premise first, against the platform. Do not extend on the
correlation.
